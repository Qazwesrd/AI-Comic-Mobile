# Android 测试版与正式版发布规则

## 1. 发布渠道（强制）

| 版本 | 允许发布渠道 | 下载规则 |
|---|---|---|
| 测试版 | 小红书测试招募帖、经确认的测试分发渠道 | 仅分发标记为“测试版”的安装包；通过账号服务端激活 48 小时试用 |
| 正式版 | 官方网站 | 只能在官方网站完成登录和永久授权核验后下载；不得通过小红书、网盘、群文件、GitHub Release/Artifact 或其他第三方渠道公开分发 |

小红书内容只能宣传和分发测试版。帖子、封面、说明和下载页必须明确标注“测试版 / 48 小时试用”，不得将测试版描述成已购买的正式版，也不得在小红书直接提供正式版 APK。

## 2. 测试版与正式版一致性

- 两个版本使用同一产品功能、界面、创作流程、AI 能力入口和服务端业务规则。
- 唯一产品差异是授权期限：测试版首次激活后连续 48 小时；正式版经服务端核实购买后获得永久授权。
- 不得为测试版隐藏功能、降低生成质量、限制项目数量或人为缩短创作链路。
- 测试版到期后不删除项目、小说、素材或配置；购买正式版后，原账号数据和授权直接恢复，无需重新导入或重新创作。

## 3. 安装包签名与升级

- 测试版和正式版必须使用同一个 Android applicationId，并使用同一发布签名证书，以支持覆盖安装和正常升级。
- 不得把 Android Debug APK 当作面向公众的小红书测试安装包；Debug APK 仅用于开发人员内部验证。
- 面向测试用户的 APK 应使用发布签名，版本号递增，并在下载说明中标注版本、构建日期、试用规则和反馈方式。
- 正式版必须使用受保护的 release keystore 签名。keystore、密码和签名密钥不得提交到仓库、写入 APK 或公开到构建日志。
- 每个公开 APK 发布时提供 SHA-256 校验值；下载页同时显示版本号、更新日志、文件大小和校验值。

## 4. 正式版官网下载保护

- 正式版 APK 只能由官方网站的正式下载入口提供。
- 下载前必须由服务端验证登录账号具有永久授权；仅创建订单、提交付款截图或客户端本地状态不得解锁下载。
- GitHub Actions Artifact 仅用于内部构建与验收，不是正式用户下载渠道。
- 正式版 APK 不得放在可绕过授权检查的永久公开直链上。应使用服务端签发的短时效下载凭证或受控存储访问，并记录下载审计。
- 官网必须拒绝试用账号、未登录用户和未核验付款用户的正式版下载请求。

## 5. 发布前检查清单

### 测试版（小红书）
- [ ] APK 明确标记为测试版，使用与正式版相同的 applicationId 和发布签名证书。
- [ ] 新账号首次激活开始服务端 48 小时计时；修改手机时间、重装或换设备不能重置试用。
- [ ] 测试版在试用期内具备正式版全部功能。
- [ ] 试用到期后核心创作操作受限，但用户数据仍可查看、导出和恢复。
- [ ] 小红书帖子明确标注测试版、48 小时试用和反馈渠道，不附正式版 APK。

### 正式版（仅官网）
- [ ] 已完成永久授权购买核验与服务端授权发放。
- [ ] APK 使用正式签名证书，签名与测试版保持一致。
- [ ] 官网未授权下载被拒绝，已授权下载成功。
- [ ] 下载链接短时有效且不能绕过服务端授权；发布 SHA-256、版本号和更新日志。
- [ ] 完成 Android 真机安装、覆盖升级、登录、创作、导出和数据恢复验收。

## 6. 当前实现状态

本规则是目标发布规范，不代表发布流水线已经完成。当前仓库 Android Actions 产物是 Debug APK；尚需完成同签名的测试发布包、正式签名密钥管理、短时效下载凭证、真实官网授权下载验收和真机覆盖升级测试。在这些项目完成前，不应把现有 Debug APK 当作可公开发布的正式测试包，也不应宣布正式版已可下载。

## 7. 已加入的签名构建工作流

仓库新增手动触发工作流 `.github/workflows/android-signed-release.yml`，支持选择 `test` 或 `production` 渠道并生成发布签名 APK。该工作流只上传保留 14 天的 GitHub Actions Artifact，不会创建 GitHub Release，也不会公开正式版下载链接。

运行前，仓库管理员必须在 GitHub Actions Secrets 中配置以下四项，测试版和正式版必须使用同一套密钥：

- `ANDROID_RELEASE_KEYSTORE_BASE64`：发布 keystore 文件的 Base64 内容。
- `ANDROID_RELEASE_KEYSTORE_PASSWORD`：keystore 密码。
- `ANDROID_RELEASE_KEY_ALIAS`：签名 alias。
- `ANDROID_RELEASE_KEY_PASSWORD`：alias 密码。

另外需要建立 GitHub Environments：
- `test-release`：测试包构建环境。
- `production`：正式包构建环境，建议启用 Required reviewers 审批。

首次使用前必须人工确认 applicationId、签名证书指纹和已有用户安装包兼容性。**不得为了让构建通过而重新生成签名密钥**，否则可能导致已安装测试版无法覆盖升级。该工作流尚需真实配置 Secrets/Environments 后执行验证；生成 Artifact 不等于已发布到小红书或官网。
